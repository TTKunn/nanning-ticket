## 项目概述

**AI南宁票务后台管理系统**是一套面向景区、园区、场馆等票务场景的综合管理原型，核心目标是建立"园区 → 项目规则 → 票种 → 库存 → 售票 → 检票 → 票据"的完整业务闭环。

### 适用场景

- 🏞️ 旅游景区（5A/4A 景区、城市公园、森林公园等）
- 🎢 主题乐园、游乐场
- 🏛️ 博物馆、展览馆
- 🚢 游船、索道、观光项目
- 🎭 演艺、活动场馆

### 核心特性

1. **多层级收费规则**：支持园区入园收费、园区内单项目收费、全包套餐收费
2. **票种分组管理**：门票、游玩票、全包票、套票分类管理
3. **双维库存体系**：总库存 + 日历库存双重控制
4. **简化购票限制**：单人限购、提交字段、渠道发布、时间窗口
5. **简化退票规则**：未使用可退、过期自动退
6. **业务操作端**：窗口售票、扫码检票、票据统一管理
7. **多渠道支持**：本地系统、网售、分销平台统一管理

## 设计理念

### 1. 业务模型优先

不是"通用票务后台"，而是针对**园区票务真实业务场景**的原型：
- 园区可能有多个收费项目（入园门票 + 游船 + 观光车 + 演艺）
- 不同收费项目对应不同的票种分组
- 需要按日历管理库存，而不是只有总库存
- 业务人员需要专门的售票、检票操作页

### 2. 渐进式设计

**本期实现**：
- 园区规则配置
- 票种分组（门票/游玩票/全包票/套票）
- 总库存 + 日库存
- 购票限制（限购、字段、渠道、时间）
- 简化退票（未使用可退、过期自动退）
- 业务端（售票、检票、票据管理）

**暂不实现**：
- 转增、激活、票据介质
- 播音设备、指定售票员
- 默认日历票
- 复杂审批流、营销活动

### 3. 角色分离

- **运营管理员**：配置园区规则、票种、库存、渠道
- **业务人员**：窗口售票、现场检票
- **财务人员**：渠道对账、结算
- **系统管理员**：账号、权限、接口配置

## 核心业务模型

### 园区与项目规则

#### 业务关系

```
园区
 ├── 收费项目1：园区入园（门票）
 ├── 收费项目2：观光车（游玩票）
 ├── 收费项目3：游船（游玩票）
 └── 收费项目4：入园+游船+观光车（全包票）

每个收费项目 → 关联一条项目规则
每条项目规则 → 可挂多个票种
```

#### 项目规则字段

| 字段 | 说明 | 示例 |
|------|------|------|
| 规则名称 | 描述收费边界 | 青秀山园区入园规则 |
| 票种分组 | 门票/游玩票/全包票/套票 | 门票 |
| 收费对象 | 园区入园/园区内单项目/多个项目打包 | 园区入园 |
| 核销方式 | 单次核销/分项目核销/双核销 | 单次核销 |
| 退票规则 | 未使用可退/过期自动退 | 未使用可退 |
| 包含项目 | 全包票时需定义包含哪些项目 | 入园+游船+观光车 |
| 适用渠道 | 本地系统/网售/分销平台 | 本地系统、网售 |

#### 典型规则示例

**门票规则**
- 规则名称：青秀山园区入园规则
- 票种分组：门票
- 收费对象：园区入园
- 核销方式：单次核销（一票一次入园）
- 退票规则：未使用可退

**游玩票规则**
- 规则名称：青秀山观光车规则
- 票种分组：游玩票
- 收费对象：园区内单项目
- 核销方式：单项目核销（每次乘坐核销一次）
- 退票规则：未使用可退

**全包票规则**
- 规则名称：邕江夜游全包票规则
- 票种分组：全包票
- 收费对象：多个项目打包
- 核销方式：入园+项目双核销（入园核销一次，登船再核销一次）
- 退票规则：未使用可退 + 过期自动退
- 包含项目：园区入园、游船项目

### 票种分组体系

#### 四大票种分组

| 分组 | 用途 | 核销方式 | 典型场景 |
|------|------|----------|----------|
| 门票 | 园区入园收费 | 单次入园核销 | 景区大门票、博物馆门票 |
| 游玩票 | 园区内单项目收费 | 单项目核销 | 观光车、游船、索道、演艺 |
| 全包票 | 入园+多项目打包 | 入园+项目双核销 | 夜游套餐、VIP 通票 |
| 套票 | 节庆或联名组合 | 分项目核销 | 春节联票、亲子套票 |

#### 票种与规则关系

```
项目规则（1）→ 票种（N）
```

一条规则下可以挂多个票种，例如：
- "青秀山园区入园规则" 下挂：成人门票、儿童门票、老人票、学生票
- "青秀山观光车规则" 下挂：单程票、往返票

### 库存管理模型

#### 双维库存设计

```
总库存：跨时间段的总可售数量
日库存：按日期维度的可售数量
```

#### 三种库存模式

| 模式 | 适用场景 | 说明 |
|------|----------|------|
| 总库存 + 日库存 | 景区门票、限流项目 | 既控制总量，也控制每日流量 |
| 仅总库存 | 长期有效票、年卡 | 不限游玩日期 |
| 仅日库存 | 演出票、节庆票 | 按日期售卖，不控制总量 |

#### 库存扣减逻辑

**总库存 + 日库存模式**：
1. 售票时同时扣减总库存和对应日期的日库存
2. 如果总库存或日库存任一为 0，则该日期不可售
3. 退票时同时回补总库存和日库存

**仅总库存模式**：
1. 售票时只扣减总库存
2. 不关心游玩日期

**仅日库存模式**：
1. 售票时只扣减对应日期的日库存
2. 不控制总量上限

#### 日历库存调整

运营人员可以按日期调整日库存：
- 节假日：增加日库存备货
- 项目维护：减少或清零日库存
- 活动预留：临时调整库存分配

### 购票限制规则

#### 四类限制

| 限制类型 | 字段 | 说明 | 示例 |
|----------|------|------|------|
| 限购数量 | 单人限购上限 | 防止黄牛囤票 | 5 张/人 |
| 提交字段 | 姓名、手机号、身份证等 | 实名制或联系方式 | 姓名 + 手机号 |
| 售卖渠道 | 本地系统、网售、分销平台 | 控制发布范围 | 本地系统 + 网售 |
| 购票时间 | 最早可购、最晚可购 | 提前预订或当天截止 | 提前 15 天、当天 18:00 截止 |

#### 典型限制组合

**景区门票**：
- 限购：5 张/人
- 字段：姓名 + 手机号
- 渠道：本地系统 + 网售 + 分销平台
- 时间：提前 30 天开售，游玩当天 16:00 截止

**演艺票**：
- 限购：4 张/人
- 字段：姓名 + 手机号 + 身份证（实名制）
- 渠道：仅网售
- 时间：提前 7 天开售，演出前 1 小时截止

---

### 检票与退票

#### 检票类型

| 类型 | 适用分组 | 说明 |
|------|----------|------|
| 入园检票 | 门票、全包票 | 在园区大门核销 |
| 项目检票 | 游玩票、套票 | 在项目入口核销 |
| 二次检票 | 全包票 | 入园检票后，登船/乘车时再检一次 |

#### 简化退票规则

当前原型只支持两种退票规则：

1. **未使用可退**
   - 票据状态为"待检票"
   - 未过有效期
   - 自动判定可退，无需审批

2. **过期自动退**
   - 超过有效期且未使用
   - 系统自动发起退款
   - 原路退回

**不支持的复杂场景**（暂不实现）：
- 已使用部分退款
- 人工审批退款
- 退款手续费
- 退款到账时间配置

### 5. 库存管理

**页面位置**：`src/components/PageInventory.vue`

**功能说明**：
- 按总库存和日库存双维度展示所有票种的库存状态
- 支持按日期查询某一天的日库存情况
- 提供"调整日库存"和"调整总库存"操作
- 库存预警提醒（剩余库存低于预警线时高亮显示）

**核心操作**：

**调整日库存**：
1. 选择票种
2. 选择适用日期
3. 输入调整后的日库存数量
4. 选择调整原因（节假日备货/活动备货/项目限流/人工修正）

**调整总库存**：
1. 选择票种
2. 输入补充数量
3. 选择补货原因（常规补货/节假日备货/活动备货/其他）

**库存状态判定**：
- 库存充足：剩余 >= 预警线
- 日库存偏低：预警线 > 剩余 >= 预警线 * 0.5
- 日库存告急：剩余 < 预警线 * 0.5
- 已售罄：剩余 = 0

**适用角色**：运营管理员

### 6. 门票售票

**页面位置**：`src/components/PageSales.vue`

**功能说明**：

**出票摘要**：
右侧实时展示：
- 园区、票种分组、票种名称
- 检票方式、退票规则
- 票面金额、出票渠道
- 今日窗口售票记录

**适用角色**：业务人员（售票员）

### 7. 门票检票

**页面位置**：`src/components/PageVerify.vue`

**功能说明**：
这是**业务人员操作端**，用于现场扫码检票或手工检票。

**检票类型**：
- **入园检票**：门票和全包票在园区大门核销
- **项目检票**：游玩票在项目入口核销

**检票记录**：
- 检票码、票据号

- 游客姓名、检票类型
- 检票时间、检票人员

## 核心业务流程

### 售票流程

```
1. 业务人员打开"门票售票"页面
   ↓
2. 选择园区 → 选择票种分组 → 选择票种 → 选择游玩日期
   ↓
3. 查看剩余日库存，输入购买数量
   ↓
4. 填写购票人信息（姓名、手机号等）
   ↓
5. 选择支付方式
   ↓
6. 确认出票
   ↓
7. 系统扣减库存（总库存 + 日库存）
   ↓
8. 生成订单和票据
   ↓
9. 票据状态：已出票 → 待检票
```

**涉及模块**：
- 门票售票（操作入口）
- 库存管理（扣减库存）
- 订单管理（生成订单）
- 票据管理（生成票据）

---

### 检票流程

```
1. 游客到达园区/项目入口
   ↓
2. 检票员打开"门票检票"页面
   ↓
3. 扫描票据二维码 或 手动输入检票码
   ↓
4. 系统验证票据有效性
   - 是否已出票
   - 是否未过期
   - 是否未检票
   - 是否符合游玩日期
   ↓
5. 验证通过 → 核销票据
   ↓
6. 票据状态：待检票 → 已检票
   ↓
7. 记录检票时间、检票人员、检票类型
```

**检票类型判定**：
- 门票：入园检票
- 游玩票：项目检票
- 全包票：入园检票 + 项目二次检票

**涉及模块**：
- 门票检票（操作入口）
- 票据管理（更新票据状态）

---

### 退票流程

```
1. 游客申请退票（或系统自动发起过期退票）
   ↓
2. 系统判定退票规则
   - 未使用可退？
   - 是否已检票？
   - 是否已过期？
   ↓
3. 符合退票规则 → 自动退款
   ↓
4. 回补库存（总库存 + 日库存）
   ↓
5. 订单状态：已支付 → 已退款
   ↓
6. 票据状态：待检票 → 已退款
```

**退票规则判定**：

**未使用可退**：
- 票据状态 = 待检票
- 未过有效期
- 自动判定可退

**过期自动退**：
- 票据状态 = 待检票
- 已过有效期
- 系统自动发起退款

**不可退**：
- 票据状态 = 已检票（已使用）
- 或不符合退票规则配置

**涉及模块**：
- 订单管理（退款入口）
- 票据管理（更新票据状态）
- 库存管理（回补库存）

---

### 票据生命周期

```
创建阶段
├── 窗口售票 → 生成票据（来源：本地系统）
├── 网售下单 → 生成票据（来源：网售）
└── 分销平台 → 回传票据（来源：携程/美团/飞猪）

使用阶段
├── 已出票 → 待检票
│   ├── 入园检票 → 已检票
│   ├── 项目检票 → 已检票
│   └── 二次检票 → 已检票
│
└── 已出票 → 退票
    ├── 未使用可退 → 已退款
    └── 过期自动退 → 已退款

终止阶段
├── 已检票（正常使用完成）
├── 已退款（退票完成）
└── 已过期（未使用且未退）
```

**涉及模块**：
- 门票售票（创建票据）
- 门票检票（更新状态）
- 票据管理（统一查看）
- 订单管理（退款操作）

### 核心设计思路

#### 1. 静态原型 + 响应式数据

- 所有数据均为静态 Mock 数据，存储在各组件的 `<script setup>` 中
- 使用 Vue 3 Composition API 管理组件状态
- 无后端接口调用，适合快速演示业务流程

#### 2. 组件化页面

- 每个功能模块对应一个独立 `.vue` 文件
- 通过 `App.vue` 的 `v-if` 切换页面显示
- `Sidebar.vue` 统一管理导航状态

#### 3. 样式设计

- 采用 CSS Variables 管理颜色、间距、圆角等设计令牌
- 响应式设计：侧边栏固定宽度 220px，主内容区自适应
- 统一组件样式：卡片、表格、按钮、表单、弹窗、标签等

#### 4. 业务逻辑模拟

- 售票流程：`computed` 计算票面金额
- 库存状态：根据剩余库存与预警线判定状态
- 票种筛选：`computed` 实现前端过滤

## 设计原则总结

### 1. 业务优先

- 不追求"通用性"，而是针对园区票务真实场景
- 先定义业务模型（园区→规则→票种→库存→售检票→票据），再设计页面
- 每个字段都有明确的业务含义

### 2. 渐进实现

- 第一版先实现核心闭环：配置、售票、检票、票据
- 暂时不做：转增、激活、复杂审批、营销活动
- 简化退票规则：只支持"未使用可退"和"过期自动退"

### 3. 角色分离

- 运营管理员：配置规则、票种、库存
- 业务人员：售票、检票
- 财务人员：对账、结算
- 不同角色看到不同的操作界面

### 4. 数据驱动

- 库存预警自动判定
- 退票规则自动执行
- 票据状态自动流转
- 减少人工干预，提高效率
